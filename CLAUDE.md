# GoLinks Browser Extensions

## Overview
Browser extensions that provide in-browser go/ links (e.g., `go/github`) that redirect to configured URLs. Available for both Chrome and Firefox with Manifest v3 compatibility.

## Architecture

### Directory Structure
```
golinks/
├── common/          # TypeScript (.ts) and other files both browsers run; the same source for both
├── chrome/          # Chrome-only: manifest.json, background.ts
├── firefox/         # Firefox-only: manifest.json, background.ts, search.ts
├── types/           # .d.ts globals for the type check (Api, Rule, per browser); never built
├── scripts/         # build.mts (emits dist/<browser>/), load-firefox.mts, screenshot.mts, lib/*.mts; run by Node's type stripping
├── tsconfig.*.json  # strict type check: base, firefox (common+firefox), chrome (common+chrome), scripts
└── dist/            # git-ignored build output: load this, zip this for the stores
```
Build with `pnpm build` (both), `pnpm build:firefox` or `pnpm build:chrome`. There is no compiler: the build emits each `.ts` as `.js` with `node:module` `stripTypeScriptTypes` (types are blanked out with spaces, so line and column numbers match the source) and copies every other file byte for byte (Node built-ins only). Only erasable syntax is allowed (`erasableSyntaxOnly`: no enums, namespaces or parameter properties); the build fails on anything else. A file name present in both `common/` and a browser folder is an error, counting the emitted name (`common/x.ts` clashes with `firefox/x.js`), so nothing is overridden silently. Manifests, `importScripts()` and the HTML keep naming the `.js` files.

The extension files are classic scripts that share globals: no `import`/`export`, no bundler. For the same reason a new top-level name in one file is visible to every other file in the type check. Edit `common/`, `chrome/` and `firefox/`, never `dist/`.

### Key Files
- `common/api.ts` - namespace shim, loaded first everywhere: `const api: Api = globalThis.browser ?? globalThis.chrome!;` (`Api` comes from `types/`, per browser). All shared code calls `api.*` (Promise-based MV3 calls, valid in both browsers).
- `common/links.ts` - link storage/retrieval from browser sync storage: one item per link, `link:<name>` -> URL (see How It Works 1-2). `readLinks()` collects the `link:*` items (lowercased names) without writing storage, for pages; `getLinks()` is `seedDefaults()` then `readLinks()`, for the background; `linkKey()`, `linksFromItems()`, `linkChanges()` (the links before/after a `storage.onChanged` event, from its `link:*` keys, for every change listener), `lowercaseLinks()`, `SHIPPED_LINKS`, `seedDefaults()` (migration, then seeding)
- `common/rules.ts` - rule generation (`get_rule()`, `escapeRegex()`), the serialised `refreshRules()` queue, `startRules()`, and the storage change listener
- `common/redirects.ts` - the one observation point for go/ redirects: `redirectFact()` (name, from, to = the actual resolved URL, requestId, tabId, time) and `observeRedirects(consumer)`, which registers the single observe-only `webRequest.onBeforeRedirect` listener (`http(s)://go/*`, main_frame) and fans facts out to consumers. Call it synchronously at the top level of a background.
- `common/linkform.ts` - the one add-link form, used by every page below. Pure logic (`checkLink()`: name/URL validation and the name-taken lookup; `linksForUrl()`: existing links for a URL, one trailing `/` ignored; `saveLink()`) and `initLinkForm(container, {name?, url?}, table?)`, which builds the form (`#link-name`, `#link-url`, `#add-btn`, `#link-existing-list`, `#link-status`) into a page's `#add-link` element. With `table` (go/help only) the controls become a `<tfoot>` of that table instead: name under Link, URL under Destination (both width 100% of their cell, so the browser's column sizing aligns them), the button spanning the usage and delete columns, messages in a full-width row; the `<form>` stays in the container and the controls point at it with `form=`. Needs `links.js`.
- `common/metrics.ts` - per-device usage metrics and the per-device id (`getDeviceId()`): pure logic (`hitName()`, `withHit()` with the rollup, `withEdit()`, `editedNames()`, `formatHits/LastHit/LastEdit()`), the serialised `updateMetrics()` queue and `startMetrics()`, which both backgrounds call synchronously at the top level to register the listeners. Needs `links.js`.
- `common/theme.css` - the design system ("Slate, green"): tokens as custom properties on `:root` (colour, type, space, radius), base styles and the component classes (`page`, `card`, `page-header`, `section-title`, `data-table` with `link-name`/`num`/`dim`/`icon-cell`, `input`/`input-mono`, `btn btn-primary`, `icon-btn`, `field`/`label`, `msg-error`/`msg-status`, `note`, `messages`). Every page links it. See "Design system" below.
- `common/styleguide.html`, `common/styleguide.css`, `common/styleguide.ts` - the style guide: an extension page no UI links to (open `styleguide.html` from the extension origin, or `pnpm screenshot styleguide`). It lists every `:root` custom property of `theme.css` (read from the stylesheet at load, so a new token shows up by itself, with its value) and shows each component class and state in static markup. No colour literals and no inline styles: the swatch, type and space rules are generated by `styleguide.ts` into a constructed stylesheet that only says `var(--token)`; `styleguide.css` is its page layout. On Firefox only the test build makes it web accessible (so the screenshot can frame it); the shipped manifest does not.
- `common/popup.html`, `common/popup.ts` - toolbar popup "Add go link" (also Alt+Shift+G): the form with the active tab's URL filled in (needs `activeTab`; only http(s) URLs), name empty and focused
- `common/index.html`, `common/index.ts` - help page for `go/help` and bare `go/`: sections "Get Started" (the go/help row) and "Links": one table (`#links`; `populateLinks()` rebuilds only the table body, so the form rows keep their text and focus) with the shared form as its footer and, on every link, hits, last hit, last edited and a delete button. Each column header (except the delete column) is a `<button class="sort-btn">` in a `<thead>` built once; the active `<th>` has `aria-sort` and an arrow (theme.css). The sort (`{ column, dir }`) is remembered per device in `storage.local.helpSort` (not synced; a missing or invalid value is the default) and applied on every re-render, live updates included
- `common/notfound.html`, `common/notfound.ts` - not-found page for unmatched go/ links: the shared form with the requested name filled in (from `?name=`), URL focused
- `common/linksort.ts` - pure sorting of the go/help Links table: `sortedNames(links, metrics, sort)`, `nextSort()`, `firstDirection()`, `validSort()`, `DEFAULT_SORT` (link A→Z). Text columns (link, destination) compare case-insensitively with `Intl.Collator` (numeric, so `a2` before `a10`); hits compare as numbers (no stat = 0); last hit and last edited as times, and a link without one ("never", "—") is after those with one in both directions; ties break by link name A→Z. A first click on a text column sorts A→Z, on hits or a time column highest/newest first; a click on the active column flips. Needs `metrics.js`.
- `common/redirectlog.ts` - the per-device redirect log (see How It Works 5): `startRedirectLog()` (both backgrounds call it synchronously at the top level, after `startMetrics()`), `logEntryFor()`, `planRedirectWrite()` (day key, the 7 day / 10,000 retention), `appendRedirectLog()` (serialised queue), `readRedirectLog()`, `noteSearchRedirect(requestId, searchUrl)` (Firefox's hook). Needs `redirects.js`.
- `firefox/search.ts` - Firefox-only pure logic: `goUrlFromSearch()`
- `chrome/manifest.json`, `firefox/manifest.json` - Manifest v3, `declarativeNetRequestWithHostAccess`, `storage`, `activeTab` and `webRequest` permissions (Firefox also `webRequestBlocking`; Chrome's `webRequest` is only for the observe-only metrics hook, and Chrome's permission docs list no warning for it); both declare `action.default_popup` and the `_execute_action` command (Alt+Shift+G)
- `chrome/background.ts` - service worker: `importScripts("api.js", "links.js", "rules.js", "redirects.js", "metrics.js", "redirectlog.js")`, then `startMetrics()`, `startRedirectLog()` and `startRules()`
- `firefox/background.ts` - event page (manifest `scripts` lists the built `api.js`, `links.js`, `rules.js`, `redirects.js`, `metrics.js`, `redirectlog.js`, `search.js`, `background.js`): `startMetrics()`, `startRedirectLog()`, host-permission warning, `startRules()`, webRequest interception (which hands the search URL to `noteSearchRedirect()`)

### How It Works
1. **Initialization**: Background script seeds the shipped default links once (below), loads the links from browser storage and creates redirect rules. There is one list of links, sync `localLinks`; every link in it is removable and overwritable, a shipped default is an ordinary link once seeded. Only `go/help` and bare `go/` (the extension's own pages) are fixed. Storage (sync): one item per link, `link:<name>` -> destination URL, `<name>` lowercase, so a write or a conflict between devices concerns one link only; `seeded:<name>` -> `true` for each shipped default that was seeded. Nothing reads links from any other key. `seedDefaults()` (`common/links.ts`, run by `getLinks()`, so by both backgrounds through `startRules()` and on every rules refresh) does, in one task serialised on `seedQueue` (startup plus the storage change it causes would otherwise both write; a failure does not block the next), migration first and then seeding, with one `storage.set` for the new items and then one `storage.remove` of the legacy items; nothing is written when there is nothing to do. **Seeding**: each shipped default without a `seeded:<name>` key is added as `link:<name>` unless that key exists (the user's link wins) and gets its `seeded:` key. A deleted default stays deleted, on every device (its `seeded:` key stays). A default shipped in a later version is seeded once, the same way. Only the defaults' own keys are written, so a device that starts before sync has downloaded the user's data cannot replace the user's list (a racing seed can at worst re-add a default deleted on another device). **Migration** (every start while a legacy `localLinks` item exists): each entry is copied to `link:<lowercase name>` unless that key already exists (of entries that differ only in case the exact lowercase one wins), then `localLinks` and the old `defaultLinks` record are removed; the old record does not count as seeded, so existing installs seed the defaults once (the intended upgrade). Idempotent: a second device migrating the same data writes the same values. Accepted edge: an old-version device that later writes `localLinks` again is migrated on its next start, which can bring back a link deleted in between. Side effect: seeding and migration write `link:*` items, so the metrics edit listener sets `lastEdit` on each seeded or migrated link.
2. **Storage Integration**: browser sync storage, so links sync across devices, one item per link (see 1). Every change listener (rules, the add-link form, go/help, metrics) reacts to a change of any `link:*` key (`linkChanges()`: `storage.onChanged` gives per-key old and new values). Quotas: Chrome sync allows 512 items, about 100 KB in total, 8 KB per item and 120 writes per minute (Firefox is similar), so the ceiling is about 500 links (the seeded markers use 8 of the items; a save that fails on quota shows "Could not save: ..." in the form).  
3. **Adding links**: three ways, one form (`common/linkform.ts`): the toolbar popup / Alt+Shift+G, the not-found page, go/help. Saving writes only `link:<name>` (lowercase; an overwrite is the same key; one `storage.set`), so the rules refresh as for any change. Deleting on go/help removes only `link:<name>`; no code writes a whole list. A name that is already a link is not overwritten until the user clicks the save button again, which then reads "Overwrite go/x (now -> <url>)". After a successful save (a confirmed overwrite too) both boxes are emptied, the status keeps showing "Saved go/x" and focus moves to the name box; a validation error or the overwrite confirm keeps what was typed. Links whose destination equals the URL in the form (a trailing `/` ignored) are listed in the form and never block another name. Names are case-insensitive (`go/GH` is `go/gh`): the form saves them lowercase, a name taken in any case is an overwrite, and the keys are always lowercase (`linksFromItems()` lowercases on reading, tolerating a stray key in another case: the exact lowercase one wins, else the last). Names must be non-empty, without `/`, `?`, `#` or whitespace, and not `help`; a URL typed without a scheme (no `://`, not `name:` + non-digit such as `mailto:`; `localhost:8080` has none) is saved as `https://<typed>`, or `http://<typed>` when the host is exactly `localhost` in any case (`localhost`, `localhost:3000/x`; `localhost.example.com`, `foo.localhost` and `127.0.0.1` still get https; an explicit scheme is kept as typed, so `https://localhost` stays https) (`withScheme()`, applied when the link is saved and when the form compares URLs: the existing-links list and the overwrite check; never at redirect time, stored links are not rewritten), a URL with a scheme must be http(s) (`ftp://` keeps the "starting with http:// or https://" error, other invalid input reads "Enter a valid URL."); the result must be a full http(s) URL (a `%s` is checked as a placeholder), since one invalid stored redirect would make every later rule update fail.
4. **Usage metrics** (`common/metrics.ts`, both browsers, per device): a consumer of `observeRedirects()` (`common/redirects.ts`: an observe-only `webRequest.onBeforeRedirect` listener on `http(s)://go/*` main_frame; it fires for declarativeNetRequest redirects in both browsers, verified by the suites) counts a hit; the decision is by name, never by comparing the redirect URL with the stored destination (a `%s` link redirects to the substituted URL) when a redirect from `go/<name>` goes somewhere other than the extension's own pages and `<name>` (first path segment, lowercased) is a saved link at that moment (`readLinks()`). Not counted: unknown names and the not-found redirect, go/help, bare go/, saving on the not-found page. Firefox's search interception is not a hit itself; the following go/x redirect is, once. `storage.local.linkMetrics`: `{ name: { count, lastHit, lastEdit, recent: [{at}], hourly: [{at, n}], daily: [{at, n}] } }`, times in Unix seconds, `count` exact forever; on each write hits older than 7 days roll into hourly buckets and hours that start more than 90 days ago into UTC daily buckets. A hit is an object so an optional field (source tag) can be added later. `lastEdit` is set when a `storage.onChanged` on a sync `link:*` item shows a destination added or changed (not a removal, not the same value). Stats of a deleted link are kept under its name. Writes are serialised on `metricsQueue`; the listeners don't wait. `storage.local.deviceId`: this device's stable id, a `crypto.randomUUID()` made once and never changed, separate from `linkMetrics` (which keeps its shape, no reshape). `getDeviceId(): Promise<string>` (in `metrics.ts`) reads it or creates it lazily; concurrent first calls share one memoised promise (one id, one write; a failure is not cached), and `startMetrics()` calls it so it exists from the start. Other features (the redirect log) reuse it; a future export pairs `{ deviceId, linkMetrics }`. go/help shows hits, last hit and last edited columns and updates live from `storage.onChanged` (local).
5. **Redirect log** (`common/redirectlog.ts`, both browsers, per device): another consumer of `observeRedirects()`. Storage: one `storage.local` key per UTC day, `redirectLog:YYYY-MM-DD` (the day of the entry's `at`), each an array of that day's entries, newest last; entry `{ at, from, link, to, tabId }`, `at` in Unix seconds; new optional fields may be added later (old entries lack them). One entry per go/ navigation, joined by `requestId`: a go/ -> go/ hop (the http -> https upgrade) is no entry, the final one keeps the first `from`; on Firefox a search interception supplies `from` (the search URL) for the go/ hop that follows, via an in-memory map with a 60 s expiry (a search that never reaches go/ logs nothing). `link` is the lowercase first path segment ("" for bare go/); `to` the final resolved destination (`%s` substituted; the not-found page for an unknown name). Unknown names are logged (metrics skip them); go/help, bare go/ and any other extension page are not (`isLoggedTarget()`: `to` inside the extension, except `notfound.html`, as `hitName()` does). The storage layer (`readRedirectDays()`, `readRedirectLog()`, the write in `appendRedirectLog()`) is kept apart from the logic, so the layout can change. A write rewrites only its entry's day key. Retention on each write: day keys whose day ended more than 7 days ago are removed (an entry exactly 7 days old may sit in a kept key), then the total is cut to the last 10,000 entries across keys, oldest keys first (`planRedirectWrite()`, pure). The first write after a start reads every key (`storage.local.get(null)`) to clear leftovers; later writes read only the last 9 days by name and remove the older names. About 137 bytes per entry as JSON: a day key of 1,000 entries is ~137 kB, the cap (10,000) ~1.4 MB in total, and only today's key is rewritten per write. `readRedirectLog()` returns the whole log in order (all keys, sorted, concatenated) for tests and a later export. writes are serialised on `redirectLogQueue`, listeners don't wait. No per-entry device id: a future export pairs `{ deviceId, redirectLog }`. No UI yet.
6. **Dynamic Updates**: Storage change listener automatically updates rules when links are modified
7. **Rule Generation**: Single `get_rule()` function (in `common/rules.ts`) handles both parameterized (`%s`) and static redirects
8. **Protocol Handling**: Firefox uses webRequest to catch bare `go/` URLs from address bar searches

### Link Types
- **Not found**: any other `go/<name>` (priority 1) redirects, by `regexSubstitution`, to the extension's `notfound.html?name=<name>` (first path segment, `api.runtime.getURL`). The regex covers the whole URL, since a substitution replaces only what it matches.
- **Case**: one rule per lowercased name, `isUrlFilterCaseSensitive: false` set explicitly; `go/GH` matches `gh`, and a `%s` parameter keeps its case (`go/cs/FooBar` passes `FooBar`).
- **Static**: `"github": "https://github.com"` → `go/github` redirects to GitHub. Matches the exact name only (regexFilter `^https?://go/<name>$`, name escaped), so `*`, `^`, `|`, `.` in a name are literal and `go/githubx` does not match.
- **Parameterized**: `"githubsearch": "https://github.com/search?q=%s"` → `go/githubsearch/query` passes `query` as parameter. regexFilter `^https?://go/<name>(?:/(.*))?$`: the parameter is everything after `go/<name>/` (`go/cs/a/b` passes `a/b`), bare `go/cs` passes an empty one, and `go/csx` does not match the `cs` rule.

## Browser-Specific Implementation

### Chrome Version (`chrome/`)
- Shared code uses `api.*` (resolves to `chrome.*`); `chrome/background.ts` is only the worker entry point
- Service worker background script with `importScripts()`
- Requires `https://go/github` format in address bar

### Firefox Version (`firefox/`)
- Shared code uses `api.*` (the shim in `common/api.ts`); `firefox/background.ts` does too (no polyfill needed)
- Event page background script with manifest `scripts` array
- Includes a `webRequest` listener to catch bare `go/github` from address bar searches. Firefox turns that text into a search on the default engine, and an extension cannot change that (no API sets `browser.fixup.*`, experiments are off on Release), so the listener is the mechanism. It watches main_frame requests on every host (`<all_urls>`, `*://*/*` in `host_permissions`), so regional and custom engines work. It redirects to `https://go/...` only when the query parameter (`q`, `p`, `query` or `text`) starts with `go/` followed by a link name, and only when the request has no `details.originUrl`. An address-bar navigation has none; a link click or form submit from a page does, so those are left alone. Pages with an opaque origin (`data:`) report no originUrl and would still be redirected.
- An interception is not logged by itself: the background passes the search URL and `details.requestId` to `noteSearchRedirect()` (common/redirectlog.ts), and the go/ redirect that follows is the log entry, with the search as its `from`. The old `storage.local.interceptions` store is gone (no migration).
- Hybrid approach: webRequest for protocol-less URLs, declarativeNetRequest for actual redirects

## Design system
One stylesheet, `common/theme.css`, for every extension page. Tokens (colours, fonts, sizes, spacing, radius) are CSS custom properties on `:root`; pages use the component classes, never inline `.style.*` in `common/*.ts` and never colour literals outside `theme.css`. Light mode only (no `prefers-color-scheme` block), system fonts only (nothing downloaded or bundled), plain CSS with no build step or dependency. Muted colours, low-contrast borders, 4 px radius. A new page links `theme.css` and reuses the classes; a new look is a new token or class there. `common/styleguide.html` is the living reference: it shows every token and component class with its states (`pnpm screenshot styleguide`). `tests/build/design.test.mjs` (run by `pnpm test`) enforces these rules and names file and line.

## Chrome/Firefox Parity
Shared code lives once, in `common/`, so it cannot drift. There is no diff-based check any more.

- **Shared**: `api.ts`, `links.ts`, `rules.ts`, `index.ts`, `index.html`, `notfound.html`. Use `api.*`, never `browser.*` or `chrome.*`, in `common/`.
- **Allowed divergence**: only the two `background.ts` files, the two `manifest.json` files and Firefox's `search.ts` (its address-bar search logic), and only for browser-specific needs: the service worker with `importScripts()` vs the event page with a manifest `scripts` array, Firefox's `webRequest` interception of protocol-less `go/` URLs, and browser-specific manifest keys. Anything both browsers do (rule generation, storage handling) goes in `common/`, not in a background file.
- **Bug fixes**: a fix in `common/` fixes both. A fix in a browser folder: check whether the other browser has the same problem and fix both in the same change, or file a follow-up todo and say so in the commit body.
- **New behavior**: features land in both extensions together. A feature limited to one browser lives in that browser's folder, and the commit body and this file say why.
- **New file**: a name must not exist in both `common/` and a browser folder (the build fails).

## Development Notes
- **Chrome**: Uses service workers with `importScripts()` 
- **Firefox**: Uses event pages with manifest `scripts` array
- **No runtime dependencies; dev dependencies are dev tooling only**: Direct browser API usage, no polyfill libraries. The devDependencies are dev tooling only: `typescript`, `@types/chrome`, `@types/firefox-webext-browser`, `@types/node` (type checking) and `@biomejs/biome` (formatter and linter), all pinned. Other devDependencies are fine to add; any runtime dependency (shipped in the extension) needs asking first.
- **Format and lint**: Biome (`biome.jsonc`, 2-space indent, double quotes, semicolons, line width 120). `pnpm format` rewrites files; `pnpm lint` (`biome check --error-on-warnings`) is read-only and `pnpm test` runs it first, so an unformatted file fails the tests. Run `pnpm format` before committing. Rules that misfire on the shared-globals classic scripts (unused top-level names, redundant `use strict`) are off for `common/`, `chrome/` and `firefox/`; each disabled rule is listed in `biome.jsonc`.
- **Types**: `pnpm typecheck` runs `tsc --noEmit` (strict) three times: `tsconfig.firefox.json` (`common/` + `firefox/` + `types/firefox.d.ts`, browser types from `@types/firefox-webext-browser`), `tsconfig.chrome.json` (`common/` + `chrome/` + `types/chrome.d.ts`, `@types/chrome`) and `tsconfig.scripts.json` (`scripts/**/*.mts`, `@types/node`). `common/` is checked against both browsers: `Api` is `typeof browser` in one and `typeof chrome` in the other, so shared code may only use what both type sets agree on. Tests stay plain JavaScript (`.mjs`) and are not type checked.
- Rules are dynamically managed via `declarativeNetRequest` 
- Storage changes trigger automatic rule updates without restart
- The shipped default links are seeded into the user's links once (How It Works 1), not merged at read time
- Firefox webRequest intercepts search queries to handle `go/github` typed directly in address bar

## Testing

### Test workflow
Setup: run `pnpm install` once in a fresh checkout. It installs the dev-only tools that `pnpm test` needs (Biome and the type-check tools); `pnpm build` itself uses only Node built-ins. Nothing ships in the extension.

Red/green with `pnpm test` only: it is fast (about a second, typecheck included, no browser, no network), so run it after every change. Run `pnpm test:full` once at the end, before a handback, commit or merge. Do not iterate on the browser suites.

```
pnpm test        # biome check + typecheck + build tests + extension unit tests + loader unit tests
pnpm typecheck   # tsc --noEmit, strict, for firefox, chrome and scripts (about 0.5 s)
pnpm test:full   # pnpm test, then test:firefox, test:chrome, test:loader:integration
```
`pnpm test:unit` runs only the extension unit tests and `pnpm test:loader` only the loader unit tests (rdp framing, profiles, prefs). `pnpm test:loader:integration` runs the loader's headless-Firefox test.

### Unit tests
`tests/unit/*.test.mjs` run the shipped classic scripts (`common/*.ts`, `firefox/search.ts`, `firefox/background.ts`) as the build emits them (`emittedSource()` in `scripts/build.mts`: the same stripping, not a second path) in a `node:vm` context with a fake `browser` (in-memory `storage.sync`/`storage.local`, `declarativeNetRequest` that rejects duplicate rule ids, recorded listeners), see `tests/unit/lib/sandbox.mjs`. Top-level `const`/`let` are not properties of the context, so tests read them with `get("expr")`. Covers (`metrics.test.mjs`) hit counting rules, the rollup boundaries (7 d, 90 d), the edit diff, serialised writes under a burst and the listeners; also regex escaping, `%s` vs static rules (end anchors, `go/csx` vs `cs`, parameter `a/b`, `*`/`|` literal in static names), rule ids and the help/root/not-found rules, default and local links, the serialised `refreshRules()` queue (no interleaving, a failure does not block), the storage listener, `goUrlFromSearch` (any host, `q`/`p`/`query`/`text`, non-matches), the interception record shape and cap, and the Firefox listener (no `originUrl` only). A new script that a background loads must be added to the load list in the test.

### Chrome

### Design guard
`tests/build/design.test.mjs` (checks in `tests/lib/design-guard.mjs`; fast, no browser, part of `pnpm test`) scans `.ts`, `.html`, `.css` and `.svg` in `common/`, `chrome/` and `firefox/` and fails, naming file and line, on: (1) a colour literal outside `common/theme.css`: `rgb()`/`hsl()`-style functions anywhere; hex in `.css` declarations (inside braces, so `#id` selectors pass); named colours as values of colour properties in `.css` and as `fill`/`stroke`/`color` attributes; in `.html`/`.ts`/`.svg` a hex counts only on a line that also names a colour property (`fill`, `color`, `background`, `border`, ...). Comments are ignored. (2) in `common/*.ts` and `common/*.html`: a write through `.style` (`.style.x`, `.style =`; reading `rule.style.getPropertyValue` is fine), `setAttribute("style")`, a `style="` attribute or a `<style>` element. (3) any `.html` page that does not link `theme.css`. Blind spots: a hex in a `.ts` string on a line with no colour property name, named colours in `.html`/`.ts` other than as `fill`/`stroke`/`color` attributes, and colours built from strings. Unavoidable uses go in `ALLOW` (file, line, rule, reason; empty now). The test also runs the checks on planted violations.

### Firefox automated tests
```
pnpm test:firefox
```
Builds `common/` + `firefox/` into a throwaway copy and installs it as a temporary add-on in headless Firefox and exits non-zero on any failure. No dependencies are installed: it uses Node 24 (`node:test`, built-in `fetch`) and raw WebDriver against the system geckodriver.

**Prerequisites**: Node 24, pnpm, snap Firefox and `/snap/bin/geckodriver`. The copy is built in `tests/firefox/.build/` (git-ignored, deleted after the run) because snap-confined Firefox cannot read `/tmp`.

**Covers**: the shared add-link form (`addlink.test.mjs`, via the harness): `go/zznew` lands on `notfound.html?name=zznew` with the name filled in and the URL focused, saving there makes `go/zznew` redirect; the popup page renders the same form; invalid names write nothing; the links for a URL are listed (trailing `/` ignored); a taken name needs the confirm, naming its current destination, before it is overwritten; go/help carries the form. The background page loads with no JavaScript errors (startup errors fail the run); `go/github`, `go/cs/test`, `http://go/gh`, `go/help`, `go/` and an unknown link; adding and deleting a link through the options form updates the redirect rules; a burst of overlapping storage writes never fails with "Duplicate rule ID" and leaves the rules for the last write; link names containing regex characters (`a.b`, `c++`) match literally; `go/csx` does not match the `cs` rule. URLs that merely contain `go/` (`https://github.com/golang/go/issues`, `https://foo.go/bar`, `?q=ago/github`, `?other=go/github`) are not redirected; a navigation with no origin to a URL carrying `go/github` in `q`, `p`, `query` or `text` on any host (what the address bar produces: google.com, google.co.uk, a custom engine) is; a link click or GET form submit from an http page to such a URL is not. Interceptions are recorded in `storage.local.interceptions` with the right `from`/`to`, a non-intercepted URL adds none, and 150 overlapping records keep only the last 100 in order.

**Metrics** (`metrics.test.mjs`): `go/github`, `go/CS/FooBar` count under the lowercase name with `lastHit` set; unknown, go/help and go/ count nothing; a search URL with `q=go/gh` counts exactly 1; adding a link sets `lastEdit` (same destination and deletion don't); go/help shows the columns. Chrome's `metrics.test.mjs` is the same without the search case.

**Does not cover**: the real toolbar click, Alt+Shift+G and the popup's prefill from the active tab (the popup is only opened as a tab, where it is the active tab itself), typing protocol-less `go/github` in the real address bar (WebDriver cannot drive it, so only the webRequest listener is exercised; WebDriver navigation stands in for typing, as neither has an originUrl), clicks from `data:` pages, the about:debugging UI, signed or permanent installs, Firefox Sync, private windows, Chrome.

Set `GOLINKS_MUTATE=<name>` (names in `tests/firefox/lib/extension.mjs`; each names the built file it edits, e.g. `rules.js` or `background.js`) to break the copy on purpose and check that a test goes red.

### Chrome automated tests
```
pnpm test:chrome
```
Builds `common/` + `chrome/` into a throwaway copy and installs it in headless Google Chrome and exits non-zero on any failure. `pnpm test:full` runs this suite after the Firefox one. No dependencies are installed: it uses Node 24 (`node:test`, built-in `fetch` and `WebSocket`) and talks to Chrome directly over the DevTools protocol, with no chromedriver.

**Prerequisites**: Node 24, pnpm and `/usr/bin/google-chrome`. The copy is built in `tests/chrome/.build/` (git-ignored, deleted after the run).

**Launch flags**: `--headless=new --no-sandbox --no-first-run --disable-gpu --enable-unsafe-extension-debugging --remote-debugging-port=<free port> --user-data-dir=<temp> --host-resolver-rules="MAP go 127.0.0.1"`. Branded Chrome ignores `--load-extension`, so the extension is installed with the DevTools method `Extensions.loadUnpacked`, which needs `--enable-unsafe-extension-debugging`. Chrome has no equivalent of Firefox's `network.dns.localDomains`, so `--host-resolver-rules` makes the `go` host resolve. Every Chrome process group started is killed on exit, Ctrl-C or SIGTERM.

**Covers**: the shared add-link form (`addlink.test.mjs`): not-found page prefill and focus, save then redirect, `go/csx/query` names `csx`, popup page, validation writes nothing, existing links listed, overwrite confirm. The service worker starts with no JavaScript errors (its console is captured from the first line); `https://go/github`, `https://go/cs/test`, `http://go/gh`, `https://go/help`, `https://go/` and an unknown link; adding and deleting a link through the options form updates the redirect rules; a burst of overlapping storage writes never fails and leaves the rules for the last write; link names containing regex characters (`a.b`, `c++`) match literally; `go/csx` does not match the `cs` rule; `https://github.com/golang/go/issues` is not redirected. Pages never touch the internet: requests that survive the extension's redirects are answered with an empty 200.

**Does not cover**: the real toolbar click, Alt+Shift+G and the popup's prefill from the active tab (opened as a tab, the popup is the active tab), typing `go/github` in the real address bar (Chrome treats it as a search; DevTools cannot drive the omnibox), `chrome://extensions`, packed or Web Store installs, Chrome Sync, incognito, Firefox.

Set `GOLINKS_MUTATE=<name>` (names in `tests/chrome/lib/extension.mjs`) to break the copy on purpose and check that a test goes red.

### Dev loader (Firefox)
```
pnpm load:firefox
```
Builds `dist/firefox/` (`common/` + `firefox/`) and installs it as a temporary add-on into your everyday Firefox, replacing the about:debugging "Load Temporary Add-on" clicks. Run it again after an edit to rebuild and reload the add-on. It talks to Firefox's Remote Debugging Protocol (what `web-ext run` uses) with `node:net` only. It does not use WebDriver/Marionette, so Firefox is not marked as automated. No dependencies. Firefox is run from `/snap/bin/firefox` (the `/usr/bin/firefox` wrapper changes desktop settings), and the add-on is installed from `dist/firefox/`, rebuilt on every run (an explicit `--addon <dir>` is installed as it is).

**Why the server is closed again**: Firefox puts its window in "remote controlled" mode (striped URL bar, robot icon, `remotecontrol` attribute on the window) for as long as a DevTools socket listens (`gRemoteControl` in `browser.js`, fed by `DevToolsSocketStatus`). `--start-debugger-server` opens such a socket, so the old loader, which left it open, left Firefox in that state. Now the server is open only for the install: the script installs the add-on, then closes the listening socket from Firefox's parent process (`DevToolsServer.closeAllSocketListeners()`, on the same server object `DevToolsStartup` made). The window loses the cue at once and nothing listens on the port. The script closes every DevTools listener in that server, not only the one on `--port`, so a server left open by the old loader or by hand is closed too (the aim is a browser that is never left remote controlled; do not use this loader alongside other debugger clients). The installed temporary add-on stays until Firefox restarts. The close relies on Firefox internals (`DistinctSystemPrincipalLoader.sys.mjs` and the `@mozilla.org/devtools/startup-clh;1` component), verified on Firefox 157 only; if a Firefox update moves them the script exits non-zero naming them and the window stays remote controlled until it restarts. This was checked against Firefox 157's own source (`omni.ja`) and by reading the attribute over the protocol before and after.

**What it does, in order**:
1. Something already speaks the debugger protocol on the port: installs or reloads the add-on, closes the server and exits. No restart.
2. Firefox is running on the profile without the server and can take a forwarded command (it was not started with `--no-remote` or `--headless`; checked from `/proc/<pid>/cmdline`): runs `firefox --profile <dir> --start-debugger-server <port>`, which Firefox forwards to the running instance (no restart, same pid; the script checks the pid did not change), then installs and closes the server as above. This is the normal edit-reload loop, and it works because an earlier run left the debugger prefs in force for that session (see Prefs). If the prefs are not in force there (you started that Firefox yourself) the server does not open; the script then falls back to step 3, and a stray extra window may open once.
3. Otherwise: asks `y/N` (or pass `--restart`), quits it with SIGTERM (a normal shutdown, never SIGKILL) and relaunches it with `--start-debugger-server`. A Firefox started with `--no-remote` (as the first version of this script did) is never sent a second `firefox` command, which would only open a "Firefox is already running" window. If Firefox does not quit within 60 s the script gives up. The tabs only come back by themselves when `browser.startup.page` is 3; otherwise use History > Restore Previous Session (the script warns).
4. Firefox is not running: launches it (normal window, without `--no-remote`, so other programs can still open links in it and step 2 works next time) with the server, then installs and closes the server.

**Prefs (temporary)**: the server needs `devtools.debugger.remote-enabled=true`, `devtools.debugger.prompt-connection=false` and `devtools.chrome.enabled=true`. They are never left in the profile. On a launch the script prints them and asks `y/N` (or pass `--set-prefs`), appends them to the profile's `user.js` (printing the exact lines), starts Firefox, and as soon as it answers removes exactly those lines again (deleting `user.js` if it created it and nothing else is in it) and, in Firefox's parent process, moves the values from the user branch to the default branch (`clearUserPref` plus `getDefaultBranch("").setBoolPref`). Default-branch values apply for the session but are never written to `prefs.js`, so after Firefox quits neither `user.js` nor `prefs.js` mentions them, and the next launch asks again. Within the session they stay in force, which is what lets step 2 reopen the server without a restart. If the script is interrupted (Ctrl-C) it removes its lines first. Prefs the profile already has set the wanted way (by you, or by an old version of this script, which saved them for good) are left alone and reported; the script prints how to remove them but never edits them. A pref the profile sets to the opposite value is an error, not overridden. Firefox's own save about 0.75 s after startup writes the user.js values into `prefs.js`, and the save that drops them after the move is debounced (about 500 ms) and skipped when Firefox gets SIGTERM in that time (measured: 7 of 8 immediate quits kept all three prefs). So the move script ends with `await Services.prefs.savePrefFile(null)`, and `prefs.js` is clean when the loader returns. Left open: a crash or SIGKILL of Firefox in the roughly 0.5 s between that startup save and the move (the loader's own launch) still leaves the three prefs in `prefs.js`; they would show up as "already set" on the next run. Verified on Firefox 157: with default-branch-only prefs a forwarded `--start-debugger-server` opened the server (same pid), and `prefs.js` had none of the three after a clean quit. A crash or SIGKILL before the lines are removed leaves them in `user.js`.

**Risk**: while the server is open, which is only for the few seconds of the install, any program on this computer (localhost only) can connect to the port, with no prompt, and fully control the browser. If the script cannot close the server it exits non-zero and says Firefox stays remote controlled until it is restarted. A temporary add-on is gone when Firefox restarts, so run the script again after each restart (the prefs go with it).

**Options** (`pnpm load:firefox -- --help`): `--profile <dir>` / `GOLINKS_FF_PROFILE` (default: the default profile from `~/snap/firefox/common/.mozilla/firefox/profiles.ini`, else `~/.mozilla/firefox/profiles.ini`), `--port <n>` / `GOLINKS_FF_PORT` (default 6005), `--addon <dir>` (default: build and use `dist/firefox`), `--binary <path>` / `GOLINKS_FF_BIN`, `--set-prefs`, `--restart`, `--headless`.

**Errors**: no profile (lists where it looked), port held by something that is not Firefox's debugger, Firefox's own message when the install is rejected, Firefox refusing to quit, and the server not closing afterwards.

**Tests**: `pnpm test:loader` is the fast unit tests for the protocol framing, profile lookup and prefs (part of `pnpm test`). `pnpm test:loader:integration` (about 40 s; part of `pnpm test:full`) is an integration test that starts headless Firefox on a throwaway profile in `tests/load-firefox/.build/` (git-ignored). It checks that the add-on's background page really runs (the test add-on calls a local HTTP server), that the debugger port is closed after every run, that a reload does not restart Firefox (same pid), that the fallback to the restart prompt is quick when the forwarded command is not taken, that the window's `remotecontrol` attribute (logged from inside Firefox) goes from `true` to `null`, that `user.js` and `prefs.js` hold none of the three prefs while Firefox runs and after it quits, and the refuse/`--restart` paths. It never reads or touches a real profile. **Does not cover**: the real profile, a non-headless window in the suite (headless Firefox has no remoting, so step 2 is only exercised as "skipped, ask to restart"; its success side, including the default-branch prefs, was run by hand in a throwaway headful profile), the visual look of the URL bar, session restore of real tabs.

## Configuration
Links are sync storage items `link:<name>` (name lowercase) with the destination URL as the value. Writing or removing one updates the rules in both browsers. Do not write `localLinks` (the legacy single item, migrated at the next start) or `seeded:*` (the record of seeded defaults).

### Chrome
```javascript
chrome.storage.sync.set({
  "link:github": "https://github.com",
  "link:newlink": "https://example.com"
});
chrome.storage.sync.remove("link:newlink");
```

### Firefox
```javascript
browser.storage.sync.set({
  "link:github": "https://github.com",
  "link:newlink": "https://example.com"
});
browser.storage.sync.remove("link:newlink");
```
